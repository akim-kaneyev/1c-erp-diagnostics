# 1C ERP Diagnostics v0.3.10 — Incident Discovery and Companion Provenance

## Summary

Version 0.3.10 adds a bounded incident-discovery path without treating public web material as case evidence. It also updates the reviewed Unica source and exposes Jev as an optional, independently installed browser-action companion.

## Changes

- Added `one-c-erp-incident-search` and a packaged standard-library bridge for the public Infoblog title index.
- Fixed the source to `https://infoblog.mywebguide.ru/data/search.json`; requests are HTTPS GET only, redirects are rejected and user query terms are not transmitted.
- Added media-type, response-size and compact-schema validation plus ETag, Last-Modified, retrieval timestamp and payload SHA-256 provenance.
- Made caching opt-in. Conditional requests revalidate cached data; explicit offline use is marked `stale_unverified`; network failure never silently falls back to stale data.
- Kept article bodies outside the repository. Returned titles and links are non-authoritative leads that require selected-page review, official-source verification and primary case evidence.
- Updated Unica to canonical marketplace release `v0.12.3`, commit `c02e38d44a7dc238310172b9d790487f81aa4fb4`, path `plugins/unica`.
- Added optional Jev browser use `0.1.0` at commit `cf7e76607d4ec70592b24becadd0296dcda8177a`. Jev remains a separate MIT-licensed plugin; it requires Node.js 22+, Codex CUA and an explicitly accepted external model provider/data destination.
- Limited Jev to reviewed mechanical browser actions. It does not type, establish 1C semantics or verify its own result, and it is not used by the deterministic Infoblog bridge.
- Expanded the stable marketplace from four to five entries and the primary plugin from 32 to 33 packaged skills.
- Clarified the rendered `settlements-chronology` contract after clean-session runtime checks exposed an ambiguous current-goal boundary: locating the first visible difference remains intermediate while the consuming mechanism is unproved, so the read-only case stays `R0 + EVIDENCE_REQUIRED`, Gate 7 passes by rejecting causality, Gate 10 remains blocked and claims remain below `УСТАНОВЛЕНО`.
- Clarified the equivalent `warehouse-first-divergence` boundary after the resumed clean-session run reproduced the same ambiguity: the visible series difference is established only as an intermediate localization, while the causal goal and linked incident stay blocked until a consuming mechanism is evidenced.
- Clarified the `post-item-expenses` bounded evidence-assessment boundary after a clean-session response promoted two supplied input facts into established claims: Gate 10 closes only the sufficiency assessment, while the setting-to-result hypothesis and linked incident remain unproved and require non-established claims.
- Reproduced the same contract defect in `production-chain-gap`, where a clean-session response emitted two `УСТАНОВЛЕНО` input-fact claims although the case permits none. The suite now rejects any zero-established case whose rendered prompt does not disclose that boundary.
- Aligned the seven remaining affected prompts (`access-rights-no-broad-grant`, `adversarial-missing-mechanism`, `production-chain-gap`, `scoped-r3-mass-repost`, `sonarqube-static-finding-no-runtime`, `unavailable-required-capability` and `vat-date-separation`) with their existing expectations. This is prompt disclosure only: expected statuses, risks, decisions, evidence and acceptance limits are unchanged.
- Reproduced two value/verification ambiguities in the externally isolated `six-row-balanced-fallback` case. After the first encoding fix, a later clean-session canary still coerced numeric `sum_share` to a boolean and treated procedural Gate 7 as requiring an external executor. Semantic prompts now name only the actual boolean markers, preserve `sum_share` as an exact numeric ratio and require the bounded internal second calculation to close Gate 7, while continuing to hide expected marker values.
- Reproduced the remaining status-scope ambiguity in the next isolated canary: all arithmetic markers and closure fields were correct, but bounded control facts were promoted to the overall `ВЕРОЯТНО` status. The case now requires `final_status=ТРЕБУЕТ ПРОВЕРКИ`, because it intentionally provides no complete causal chain for a real incident.
- Reproduced a strict-enum defect in the full clean-session run: the model proved the complete six-stage chain but emitted descriptive `stage` synonyms that the published schema correctly rejects. The rendered contract and `complete-cost-chain` prompt now expose the exact ordered enum (`document`, `movement`, `record_register`, `consuming_mechanism`, `accounting_stock_access_result`, `symptom`) and its evidence mapping; validator expectations remain unchanged.
- Reproduced the next `complete-cost-chain` canary defect after the stage enum passed: the model emitted six established evidence-summary claims instead of one material conclusion. The case now requires exactly one chain-level `УСТАНОВЛЕНО` claim using E-CC-1–E-CC-6 and explicitly forbids per-stage claim restatements; the existing validator limit remains unchanged.
- Reproduced a later full-run closure defect in `vat-date-separation`: the model correctly kept the bounded comparison below `УСТАНОВЛЕНО`, but closed the current goal with Gate 7 still blocked. The case now requires Gate 7 to pass after a distinct second comparison of E-VAT-1/E-VAT-2/E-VAT-3 and makes explicit that this procedural pass does not establish a cause or correct tax accounting.
- Reproduced the next `patch-redistributes-without-completeness-change` defect: the runtime omitted the fallback row from the before totals and converted a read-only request for business justification into `R2 + NO-GO` with an action object. The case now states the full-row totals, requires `R0 + EVIDENCE_REQUIRED`, closes the bounded assessment through procedural Gate 7/8/10, and keeps the missing business basis in `requested_evidence` with `actions=[]`.
- Reproduced a later `historical-residual-numeric-coincidence` defect: the runtime left the bounded identity assessment blocked, treated the linked causal incident as out of scope, omitted E-NC-1 from the supplied alternative arithmetic and promoted the causal marker to `УСТАНОВЛЕНО`. The case now closes only the current assessment, keeps the incident blocked, includes 10+10=20 in E-NC-1 provenance and requires three established control facts plus one `ТРЕБУЕТ ПРОВЕРКИ` causal claim.
- Reproduced the equivalent scope defect in `shared-predicate-controls-fact-and-plan`: the runtime computed every marker correctly but left the bounded reachability goal and Gate 7 blocked. The case now closes the trace-limited assessment through Gate 7/8/10, keeps actual runtime behavior blocked, and preserves `fact_stays_plan_zero_reachable` below `УСТАНОВЛЕНО`.
- Reproduced the release-boundary scope defect in `identical-release-code-does-not-prove-persistent-bug`: all three control conclusions were correct, but the runtime left the bounded sufficiency assessment and Gate 7 blocked. The case now closes only that assessment through an independent counterevidence recheck, keeps the linked incident blocked and does not promote code identity into proof of a persistent defect.
- Reproduced the validation-ladder defect in `static-pass-is-not-accounting-pass`: the runtime correctly blocked the R2 load but marked the incident out of scope, skipped evidence coverage, passed Gate 7 and cited only the accounting-effect row for the failed accounting step. The case now keeps the authorization goal and incident open/blocked, requires the static-plus-effect evidence mapping and preserves Gate 7/9/10 as blocked until business and accounting validation exist.
- Rejected later canary runs after proving that plain-text `@one-c-erp-diagnostics` did not activate the primary plugin and that web/shell searches could expose `PUBLISHING.md`, eval expectations and prior local sessions. Runtime prompts now carry the exact `plugin://` mention and prohibit all model tools; schema-2 acceptance hashes each complete Codex log, validates the mention/no-tools policy and binds the cross-platform canonical installed-plugin tree hash and current source commit.
- Preserved the strict `EVAL_RESULT_JSON` suite, approved Velis assets and existing Gate 0–10 controls.

## Release boundary

Repository validation, protected Pull Request CI, CodeQL, merge, tag/release and installed-runtime acceptance are separate claims. This candidate must not be described as runtime-accepted until exact installed v0.3.10 completes the full 26-case clean-session run and `tools/validate_runtime_run.py` validates its hash manifest.

The historical v0.3.8 run and repository-local tests do not accept the changed package. Jev live provider/browser behavior and installed Unica execution also require host-side confirmation.
